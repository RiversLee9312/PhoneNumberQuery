# China allocation data cross-check

## Finding

The reported lookup for `13808880000` is consistent across three offline datasets: the bundled JPHN asset and the pinned 2023 `ls0f/phone` database both map prefix `1380888` to Guangdong / Guangzhou, and the Google libphonenumber v9.0.41 English geocoder returns `Guangzhou, Guangdong`. The `13800138000` control is also consistent: both databases map `1380013` to Beijing / Beijing, and Google's geocoder returns `Beijing`.

This resolves the specific suspicion that `1380888` should map to Yunnan / Kunming. The cross-check supports retaining the JPHN supplemental table, while not treating it as independently verified ground truth for every prefix.

## Reproducible sources and method

- **Current table:** JPHN v2 from [jieeit/phone at commit `e963c60de92383ca2c32eb318b10c469b34d11a4`](https://github.com/jieeit/phone/commit/e963c60de92383ca2c32eb318b10c469b34d11a4), file [`src/data/phone.dat`](https://github.com/jieeit/phone/blob/e963c60de92383ca2c32eb318b10c469b34d11a4/src/data/phone.dat). It has 520,170 seven-digit prefixes. The included asset SHA-256 is `7D0740136B98D7DBEE9A1C917E60D10453C739463898082D2CC1B9DCCB55D5BB`.
- **Historical cross-check:** [ls0f/phone commit `08c48e8e711f9a435dad7c14efba148172465f72`](https://github.com/ls0f/phone/commit/08c48e8e711f9a435dad7c14efba148172465f72), file [`phone/phone.dat`](https://github.com/ls0f/phone/blob/08c48e8e711f9a435dad7c14efba148172465f72/phone/phone.dat). Its README states a December 2023 update and 499,527 records. The file is 4,505,816 bytes; SHA-256 `cb17a69eafa68d7706cfcc68d47cdf165ea916e9d5c476b4dd5f06cf74aed23d` (Git blob `4436d27bfdc58ae608c204b061180c8200c5bd57`).
- **Google geocoder:** the app's exact Maven artifacts (`libphonenumber:9.0.41`, `geocoder:3.41`, `prefixmapper:3.41`) were run locally with `PhoneNumberOfflineGeocoder`. The official v9.0.41 sources are [the geocoder implementation](https://github.com/google/libphonenumber/blob/v9.0.41/java/geocoder/src/com/google/i18n/phonenumbers/geocoding/PhoneNumberOfflineGeocoder.java) and the bundled [China English map](https://github.com/google/libphonenumber/blob/v9.0.41/java/geocoder/src/com/google/i18n/phonenumbers/geocoding/data/86_en) / [China Chinese map](https://github.com/google/libphonenumber/blob/v9.0.41/java/geocoder/src/com/google/i18n/phonenumbers/geocoding/data/86_zh). For `+8613808880000`, the local Java result was `valid=true`, `en=Guangzhou, Guangdong`; for `+8613800138000`, `valid=true`, `en=Beijing`.

The prefix comparison decoded every record in both binary files and compared `(province, city)` for all shared seven-digit prefixes; it did not sample or select only the disputed example. The JPHN file contained 520,170 records, the pinned historical file contained 499,527, and 499,502 prefixes appeared in both. Of those shared prefixes, 490,724 had an exact province-and-city match (98.2426%); 8,778 differed (1.7574%), including 1,785 province differences. The historical file had 25 prefixes absent from JPHN, while JPHN had 20,668 prefixes absent from the historical file.

Some differences may reflect changed administrative boundaries or differing area granularity rather than a definite incorrect attribution. The `ls0f/phone` comparison is a historical third-party cross-check, not an authoritative telecom registry and not necessarily independent of all upstream inputs to JPHN. Google's geocoder provides independent confirmation for the reported examples, but its China prefixes are not a complete audit of all JPHN rows. The supported conclusion is that the suspected `1380888` attribution is not contradicted by these checks, and that JPHN broadly agrees with the historical table on their shared prefixes; individual outliers still warrant review before being treated as definitive.
